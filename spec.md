# taskpad — Task Management CLI

## 1. Overview

### Purpose

taskpad is a lightweight, deterministic task management CLI tool designed for AI-assisted development workflows. It provides a single source of truth for task status while keeping task descriptions as plain Markdown files.

### Design Principles

- **Single source of truth**: All task metadata lives in one file (`status.yaml`). No duplication across files.
- **No frontmatter**: Task description files (`T*.md`) are pure Markdown with no YAML/JSON frontmatter.
- **AI-agent friendly**: Structured output, predictable behavior, no crashes on edge cases.
- **Deterministic**: Same inputs always produce same outputs. No randomness, no side effects.
- **Zero privileges**: Installation requires no root/sudo access.

### Use Cases

- Solo developers using AI agents for code generation
- Small teams tracking implementation tasks
- Projects with sequential task execution (one task at a time)
- Any workflow where task status needs to be machine-readable and human-editable

## 2. Architecture

### File Structure in Target Project

```
project-root/
├── specs/
│   └── tasks/
│       ├── status.yaml          # Single source of truth (all metadata)
│       ├── T001-project-setup.md  # Task description (plain markdown)
│       ├── T002-asset-acquisition.md
│       └── ...
└── ...
```

### How CLI Interacts with Files

```
User/AI Agent
    │
    ▼
┌─────────────────────┐
│  taskpad CLI        │
│  (reads/writes)     │
└─────────┬───────────┘
          │
          ├──► status.yaml   (metadata: status, deps, phases)
          │
          └──► T*.md         (descriptions: goal, steps, criteria)
```

### Data Flow

1. `taskpad init` — Scans directory, creates `status.yaml` if not exists
2. `taskpad new <name>` — Creates `T*.md` file + adds entry to `status.yaml`
3. `taskpad do <id>` — Updates `status.yaml` (pending → in_progress)
4. `taskpad done <id>` — Updates `status.yaml` (in_progress → done)
5. `taskpad status` — Reads `status.yaml`, displays formatted table
6. `taskpad next` — Reads `status.yaml`, finds next unblocked task

## 3. Data Model

### Status Enum

```cpp
enum class Status {
    Pending,
    InProgress,
    Done
};
```

### Task Struct

```cpp
struct Task {
    std::string id;              // "T001"
    std::string name;            // "Project Setup"
    Status status;               // Pending, InProgress, Done
    std::vector<std::string> depends;  // ["T002", "T003"]
    int phase;                   // 0-6
    bool critical;               // Part of critical path
    std::vector<std::string> files;    // Files to create/modify
    std::vector<std::string> specs;    // Spec references
};
```

### ProjectConfig Struct

```cpp
struct ProjectConfig {
    std::map<int, std::string> phases;      // {0: "Scaffolding", 1: "Foundation", ...}
    std::vector<std::string> criticalPath;  // ["T001", "T003", "T010", ...]
};
```

### T*.md Template

```markdown
# T001: Project Setup

## Goal

Set up project structure, Makefile, directory tree, .gitignore, and a stub main.cpp that opens a window.

## Depends On

(None)

## Spec References

- `raylib-cpp/00-project-setup.md` → "Project Structure" and "Makefile" sections
- `raylib-cpp/05-coding-style.md` → "General Rules" section

## Files to Create/Modify

- `Makefile` (MODIFY or CREATE)
- `.gitignore` (MODIFY or CREATE)
- `src/main.cpp` (NEW or MODIFY)

## Implementation Steps

1. Create the directory tree under the project root
2. Write a Makefile with debug, release, run, and clean targets
3. Create or update `.gitignore` to exclude build artifacts
4. Create a stub `src/main.cpp` that initializes a raylib window

## Constraints

- Must use `game::` namespace for all game code
- `#pragma once` header guard for all headers
- Follow naming conventions in `specs/raylib-cpp/05-coding-style.md`

## Acceptance Criteria

- [ ] `make` compiles without errors
- [ ] `make run` opens a window
- [ ] `make clean` removes build artifacts

## Notes

( filled in during/after implementation )
```

### Directory Structure Conventions

- Task files: `TXXX-kebab-case-name.md` (e.g., `T001-project-setup.md`)
- Status file: `status.yaml` (always in same directory as task files)
- Task IDs: Zero-padded 3-digit numbers (T001, T002, ..., T999)

## 5. CLI Commands

### taskpad init

Initialize task tracking in the current project.

```bash
$ taskpad init
Initialized taskpad in specs/tasks/
Created status.yaml
Ready to add tasks with `taskpad new`
```

**Behavior:**
- Creates `specs/tasks/` directory if it doesn't exist
- Creates empty `status.yaml` if it doesn't exist
- If `status.yaml` already exists, reports "Already initialized"
- Does NOT scan existing T*.md files (start fresh)

### taskpad new <name>

Create a new task.

```bash
$ taskpad new "Project Setup"
Created T001-project-setup.md
Updated status.yaml

Edit T001-project-setup.md to add:
  - Goal
  - Depends On
  - Spec References
  - Implementation Steps
  - Acceptance Criteria
```

**Behavior:**
- Generates next available task ID (T001, T002, ...)
- Converts name to kebab-case for filename
- Creates T*.md file from template
- Adds entry to `status.yaml` with status=pending
- Task ID is auto-incremented, never reused

### taskpad status

Show all tasks with their status.

```bash
$ taskpad status
Phase 0: Scaffolding
  T001  Project Setup         [done]
  T002  Asset Acquisition     [in_progress]

Phase 1: Foundation Types
  T003  Core Types            [pending]  ← next (dependencies met)
  T004  ResourceManager       [pending]  ← blocked by T002
  T005  Layout System         [pending]  ← blocked by T001
  ...

Progress: 1/30 done, 1 in_progress, 28 pending
```

**Behavior:**
- Reads `status.yaml`
- Groups tasks by phase
- Shows status in brackets: [pending], [in_progress], [done]
- Marks next available task with ← next
- Shows blocked tasks with ← blocked by TXXX
- Displays progress summary at bottom

### taskpad next

Show the next task to work on.

```bash
$ taskpad next
Next: T003 — Core Types
  Depends on: T001 [done] ✓
  Goal: Core types, enums, components, entities
  First step: Create src/core/types.h with game:: namespace
  Files: src/core/types.h, src/core/types.cpp
  Specs: raylib-cpp/01-architecture.md, game/01-core-concepts.md
```

**Behavior:**
- Finds all tasks with status=pending
- Filters to tasks where all dependencies are done
- Prioritizes: critical path first → phase number → task number
- Displays task details from `status.yaml`
- Reads first implementation step from T*.md file
- If no tasks available, shows "All tasks blocked or complete"

### taskpad do <id>

Start working on a task.

```bash
$ taskpad do T003
Started T003 — Core Types
Status changed: pending → in_progress

Now reading T003-core-types.md...
```

**Behavior:**
- Validates task ID exists
- Checks all dependencies are done (warns if not)
- Updates `status.yaml`: status = in_progress
- Reads and displays task goal and first implementation step
- If task is already in_progress, reports "Already in progress"
- If task is done, reports "Already completed"

### taskpad done <id>

Mark a task as complete.

```bash
$ taskpad done T003
✓ T003 marked as done

Unblocked tasks:
  T009  Board Generation      [pending]
  T010  Item System           [pending]
  T013  Account System        [pending]
  T015  Level Config          [pending]
```

**Behavior:**
- Validates task ID exists
- Updates `status.yaml`: status = done
- Scans for tasks whose dependencies are now all done
- Displays unblocked tasks
- If task is already done, reports "Already completed"

### taskpad pause <id>

Pause a task (revert to pending).

```bash
$ taskpad pause T003
Paused T003 — Core Types
Status changed: in_progress → pending
```

**Behavior:**
- Validates task ID exists
- Updates `status.yaml`: status = pending
- If task is already pending, reports "Already pending"

### taskpad deps <id>

Show dependency information for a task.

```bash
$ taskpad deps T012
T012 depends on:
  T003  Core Types            [done] ✓
  T010  Item System           [done] ✓
  T011  Combat System         [in_progress] ✗

Tasks waiting on T012:
  T016  Turn Flow             [pending]
```

**Behavior:**
- Shows what the task depends on (with status)
- Shows what depends on this task
- Marks satisfied dependencies with ✓
- Marks unsatisfied dependencies with ✗

### taskpad log <id> <message>

Append a log entry to the task's markdown file.

```bash
$ taskpad log T003 "Fixed namespace issue in types.h"
Logged to T003-core-types.md
```

**Behavior:**
- Validates task ID exists
- Appends timestamped entry to `## Notes` section in T*.md
- Format: `- [YYYY-MM-DD HH:MM] <message>`
- Creates `## Notes` section if it doesn't exist

### taskpad edit <id>

Edit task metadata interactively or via flags.

```bash
# Edit status
$ taskpad edit T003 --status done
Updated T003 status: done

# Edit phase
$ taskpad edit T003 --phase 2
Updated T003 phase: 2

# Edit dependencies
$ taskpad edit T003 --depends T001,T002
Updated T003 depends: T001, T002
```

**Behavior:**
- Validates task ID exists
- Updates specified fields in `status.yaml`
- Supports: --status, --phase, --critical, --depends, --files, --specs
- Shows confirmation message

### taskpad summary

Show overall progress statistics.

```bash
$ taskpad summary
Task Summary
─────────────
Total tasks:    30
Done:            5 (16.7%)
In progress:     1 (3.3%)
Pending:        24 (80.0%)

By Phase:
  Phase 0: 2/2 done
  Phase 1: 1/6 done
  Phase 2: 2/7 done
  Phase 3: 0/1 done
  Phase 4: 0/6 done
  Phase 5: 0/3 done
  Phase 6: 0/5 done

Critical Path: T001 → T003 → T010 → T011 → T012 → T016 → T024
  Status: 3/7 done, 1 in_progress, 3 pending
```

**Behavior:**
- Reads `status.yaml`
- Calculates percentages
- Groups by phase
- Shows critical path status

### taskpad remove <id>

Remove a task.

```bash
$ taskpad remove T030
Removed T030 — Final Polish
Updated status.yaml
```

**Behavior:**
- Validates task ID exists
- Removes entry from `status.yaml`
- Optionally removes T*.md file (asks for confirmation)
- Warns if other tasks depend on this task

## 6. Error Handling

### Error Format

All errors must return structured output that AI agents can parse:

```
error: <message>
```

No stack traces, no debug output, no unexpected crashes.

### Edge Cases

| Case | Behavior |
|------|----------|
| Task ID not found | `error: Task T999 not found` |
| Invalid task ID format | `error: Invalid task ID format. Expected TXXX (e.g., T001)` |
| Task already in_progress | `error: Task T003 already in progress` |
| Task already done | `error: Task T003 already completed` |
| Dependencies not met | `warning: Task T003 depends on T002 (pending). Proceed anyway? [y/N]` |
| Circular dependency | `error: Circular dependency detected: T003 → T005 → T003` |
| status.yaml missing | `error: Not initialized. Run 'taskpad init' first` |
| status.yaml malformed | `error: Invalid status.yaml format. Expected YAML mapping` |
| T*.md missing | `warning: Task file T003-core-types.md not found. Creating template.` |
| No tasks available | `info: All tasks blocked or complete` |
| Directory not writable | `error: Cannot write to specs/tasks/. Check permissions.` |
| Empty task name | `error: Task name cannot be empty` |
| Duplicate task name | `warning: Task with similar name exists: T005-layout-system.md` |

### Validation Rules

- Task IDs must match pattern `T[0-9]{3}` (T001-T999)
- Task names must be non-empty
- Dependencies must reference existing task IDs
- Status values must be one of: pending, in_progress, done
- Phase numbers must be non-negative integers

### Build System

Use a simple Makefile (no CMake needed for this project size):

```makefile
CXX = g++
CXXFLAGS = -std=c++17 -Wall -Wextra -O2
DEBUG_FLAGS = -g -O0 -DDEBUG

SRCDIR = src
BUILDDIR = build
TARGET = taskpad

# Sources
SRCS = $(wildcard $(SRCDIR)/*.cpp)
OBJS = $(patsubst $(SRCDIR)/%.cpp, $(BUILDDIR)/%.o, $(SRCS))

# Libraries
LIBS = -lyaml-cpp

.PHONY: all clean install test debug

all: $(TARGET)

$(TARGET): $(OBJS)
	$(CXX) $(CXXFLAGS) -o $@ $^ $(LIBS)

$(BUILDDIR)/%.o: $(SRCDIR)/%.cpp | $(BUILDDIR)
	$(CXX) $(CXXFLAGS) -c -o $@ $<

$(BUILDDIR):
	mkdir -p $(BUILDDIR)

debug: CXXFLAGS += $(DEBUG_FLAGS)
debug: clean all

clean:
	rm -rf $(BUILDDIR) $(TARGET)

install: $(TARGET)
	install -d $(HOME)/.local/bin
	install -m 755 $(TARGET) $(HOME)/.local/bin/

test: $(TARGET)
	./tests/run_tests.sh

uninstall:
	rm -f $(HOME)/.local/bin/$(TARGET)
```

## 8. Testing

### Framework

Use **doctest** (header-only, single file):

```cpp
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include "doctest.h"
```

**Installation:**
```bash
# Download single header
wget https://raw.githubusercontent.com/doctest/doctest/v2.5.3/doctest/doctest.h -O tests/doctest.h
```

### Test Organization

| Test File | Coverage |
|-----------|----------|
| `test_models.cpp` | Task struct, Status enum, ProjectConfig |
| `test_storage.cpp` | YAML read/write, file I/O |
| `test_commands.cpp` | Command logic (init, new, status, next, etc.) |
| `test_validator.cpp` | Input validation, edge cases |

### Test Examples

```cpp
// test_models.cpp
#include "doctest.h"
#include "models.h"

TEST_CASE("Task ID formatting") {
    CHECK(taskpad::formatTaskId(1) == "T001");
    CHECK(taskpad::formatTaskId(42) == "T042");
    CHECK(taskpad::formatTaskId(999) == "T999");
}

TEST_CASE("Status string conversion") {
    CHECK(taskpad::statusToString(taskpad::Status::Pending) == "pending");
    CHECK(taskpad::statusToString(taskpad::Status::InProgress) == "in_progress");
    CHECK(taskpad::statusToString(taskpad::Status::Done) == "done");
}

TEST_CASE("Dependency validation") {
    taskpad::Task t;
    t.id = "T003";
    t.depends = {"T001", "T002"};
    
    std::map<std::string, taskpad::Task> tasks;
    tasks["T001"] = {.id = "T001", .status = taskpad::Status::Done};
    tasks["T002"] = {.id = "T002", .status = taskpad::Status::Pending};
    
    auto result = taskpad::validateDependencies(t, tasks);
    CHECK(result.hasError());
    CHECK(result.errorMessage() == "Dependency T002 is not done");
}
```

```bash
cd /path/to/taskpad
make
make install
```

```bash
make install PREFIX=~/bin
```

```bash
make uninstall
```

```markdown
1. When user asks "what should I work on?", run `taskpad next`
```

## Appendix D: YAML Schema Validation

The `status.yaml` file must conform to this structure:

```yaml
# Required keys
tasks:                    # Mapping of task ID to task object
  T001:                   # Task ID (string, pattern: T[0-9]{3})
    name: string          # Task name (non-empty)
    status: enum          # pending | in_progress | done
    depends: list[string] # List of task IDs
    phase: int            # Non-negative integer
    critical: bool        # true | false
    files: list[string]   # List of file paths
    specs: list[string]   # List of spec references

# Optional keys
phases:                   # Mapping of phase number to name
  0: string
critical_path: list[string]  # List of task IDs
```

**Validation rules:**
- All task IDs must match pattern `T[0-9]{3}`
- All dependencies must reference existing task IDs
- No circular dependencies allowed
- Phase numbers must be non-negative integers
- Task names must be non-empty strings
